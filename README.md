# Access Log Analyzer
## Description
Access Log Analyzer is a tool that I created for my Final Project for the CS50P course. Its a tool that reads web server access logs, in the Apache format, and prints a short, readable report. A busy web server writes one line to its log for every request, which quickly adds up to thousands of lines that nobody can read by eye. This command-line tool, written in Python, summarizes how many requests were made, how many of them failed, which status codes were returned, which IP addresses were the busiest and which IPs produced an unusually high number of errors.

Given my interest in cybersecuriy and DevOps, I've decided to create a tool to parse logs, since reading logs is a daily task. I wanted to build something that I can reuse later and I plan to extend it with other log formats, implement a system health checker and a security audit tool, on top of that. A parser for authentication logs to detect failed SSH logins, would also be a neat idea.


The report contains five parts:
 - Name of the log file;
 - Total amount of requests;
 - Error rate percentage (amount of error status codes per 100 logs);
 - Status codes, sorted by most frequent;
 - Top 5 most busy IPs;
 - Top suspicious IPs (ones with the most error codes).

If no argument (or too many) is given, the program prints a usage message and exits. If the log file does not exist, or contains no valid log lines, it exits with a clear error message.

## Files
- `project.py` contains the whole program. It has a compiled regular expression `PATTERN`, a `THRESHOLD` constant and the following functions:
 - `parse_log(log)` matches the log line against `PATTERN` and returns a dictionary with the values for the IP, timestamp, method, path, protocol, status, size, referer and user agent keys. In this function, the status and size are converted to integers and the timestamp becomes a timezone-aware `datetime`, per the [datetime documentation](https://docs.python.org/3/library/datetime.html). If the line doesn't match, it returns `None`;
 - `load_entries(path)` opens the log file, parses each entry in file with `parse_log`, skips lines that return `None` and returns a list of entries;
 - `count_statuses(entries)` returns a counter of how many times each status code appears;
 - `error_rate(entries)` returns the fraction of entries with a status of 400 or higher. In case there are no error codes in the log file or there are no entries in the log file, it returns 0;
 - `top_ips(entries, n)` returns the *n* most frequent IPs as `(ip, count)` tuples;
 - `flag_suspicious(entries, threshold)` counts error responses per IP and returns the IPs that have counts equal to or above the threshold, from highest to lowest;
 - `format_report(entries, path)` builds the full report and returns it as a single string;
 - `main()` reads the file name/path, using `sys.argv`, handles errors and prints the report;
- `test_project.py` containts the `pytest` tests for the functions above, using hand-built data.
- `requirements.txt` lists the libraries needed to run the tests (`pytest`). The program itself only uses the standard library.

## Design choices
A properly done regular expression, with named groups, can pull a lot of weight. I opted to pair this solution with *re*'s `groupdict()` to get a ready-made dictionary with all the properly parsed information.

Each function does its own analysis, which makes it very easy to test. It also allows for future reuse, since a future log format would only need a new regular expression, producing the same dictionaries.

On the `parse_log` function, I opted to return `None` on malformed lines. This allows the `load_entries` function to simply skip malformed lines, instead of interrupting the function all together.

One `THRESHOLD` constant, so that the `flag_suspicious` function and `format_report` function can never disagree.

I opted to separate the report building from the `main` function, in order to be able to return a string instead of printing it, allowing me to test it. `main` is as clean as it should be, only dealing with command-line input and errors.

You can find further information on each function and test on the comments of `project.py` and `test_project.py`.

## Sample data
This tool was developed and tested using dummy logs generated by the open-source tool [Fake-Apache-Log-Generator](https://github.com/kiritbasu/Fake-Apache-Log-Generator). **No real server data was used**.

You can find a pair of files containing sample logs to try out the tool in the [dummy sample data](<dummy sample data>) file. One of them will give you a normal output, the "healthy" one, and the other will print more errors, the "suspicious" one.

## Testing
Run the tests with:
```
pytest test_project.py
```
As previously mentioned, you can find further explanation for each test in the comments of the `test_project.py` file.

## Usage Example
To run the tool, simply run the python script, followed by the log file you want to parse, as an argument. For example, lets suppose I want to analyze a "file.log" log file:
```
python3 project.py file.log
```
